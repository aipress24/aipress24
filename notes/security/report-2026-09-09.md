# Security review, 2026-09-09

> **Remediated the same day.** Findings 1 and 2 are fixed and covered by
> regression tests; finding 3 is closed by deleting the workflow. The three
> open questions are answered at the end. What follows is the review as it
> stood, with a « Fixed » note under each finding — the reasoning is worth
> keeping even once the code has moved.

Audited the exposed surface — routes and views, the Stripe webhook, uploads, KYC, API v1, authentication and the doorman — plus the four CI workflows, against `notes/security/threat-model.md`. **5 candidate findings, 2 confirmed, 1 confirmed in part, 2 refuted.** Every candidate went to a subagent in a clean context and was told to disprove it; all five are accounted for below.

The two confirmed findings are both reachable by the adversary the threat model puts first: a signed-in member of another organisation.

## Confirmed

### 1. Any journalist can read *and overwrite* another journalist's avis d'enquête — **high, new**

`src/app/modules/wip/crud/cbvs/_base.py:545`

`BaseWipView._get_model` is `repo.get(id)` — a primary-key fetch with no owner clause. `AvisEnqueteWipView.before_request` (`avis_enquete.py:217-228`) gates on `user_can_access_newsroom`, which is one role lookup (`pr_access.py:91-98`) and passes for every journalist on the platform. `get`, `edit` and `ciblage` then fetch by id alone.

Verification ran the exploit against the real application with two PRESS_MEDIA journalists in different organisations:

```
GET /wip/avis-enquete/<id>/          -> 200, victim's data
GET /wip/avis-enquete/edit/<id>/     -> 200
GET /wip/avis-enquete/<id>/ciblage   -> 200
POST /wip/avis-enquete/  (_action=save, id=<id>, fields)
     -> 302 ; title now "PWNED BY RIVAL", owner still the victim
DELETE                                -> refused (deleted_at unchanged)
```

**This is a write, not a leak.** I filed it as read-and-edit; it overwrites the record in place with the owner unchanged. Worse, the `confirm` branch of `ciblage` calls `store_contacts`, which stamps `journaliste=avis.owner` (`avis_enquete_service.py:546-553`) and flips the status to `PUBLIC` — so an attacker driving that screen sends solicitations **attributed to the victim**. That is the editorial-integrity asset, not just the personal-data one.

The attacker needs only the id, and the application hands it over: `opportunities.j2:38` renders a link carrying `contact.avis_enquete.id` on the page of every contacted party, and journalists are targetable as experts. Failing that, ids are Snowflakes (`lib/snowflakes.py:87-102`), so ids minted close together are adjacent and walkable.

**Two corrections to what I filed.** Article is *not* affected — `ArticlesWipView._require_author` (`articles.py:378-381`) raises `Forbidden` on `owner_id != g.user.id` and is applied at get, edit, publish, unpublish and post, pinned by `TestArticleAccessControl`. I was wrong about it. **Communiqué (`communiques.py:188`) and Commande (`commandes.py:101`) do share the defect** — role-only gates over the unscoped base. They were not separately verified and are reported as unverified below.

`delete` holds, because `_base.py:472` checks the owner explicitly. That is the tell: the omission is per-route, not a decision.

**Fixed — but not the way this recommended.** The report proposed an
override on `AvisEnqueteWipView`. That would have left the same hole open in
Communiqué, Commande and — found while fixing — Events, whose `get` and `edit`
were also unguarded: the accreditation work had put the rule on one screen
(`_require_organiser`, called from a single route) and not on the fetch.

So the rule moved to the base. `BaseWipView._get_model` now refuses a record
`_can_access` rejects, and the default is the owner alone, mirroring
`BaseDataSource._base_query`. Four views widen it deliberately: Sujet (its
existing rédac-chef rule, converted), Commande (both parties, per #0225),
Events (organiser or events-mission holder, reusing `_require_organiser`'s
predicate), Avis d'enquête (the two parties of an RDV contact, per #0173 —
missed on the first attempt, which broke eleven tests and is exactly why the
suite exists). That way round fails safe: a new route inherits the check and a
wider rule has to be written on purpose.

Two now-unreachable guards were removed rather than left to mislead:
`ArticlesWipView._require_author` and the inline owner check in `notify`. Both
tested the same condition the base now tests first.

**One user-visible change**, called out for veto: a refusal is now `404`
where Article and Events previously answered `302` with `X-Access-Denied`.
That is existence-hiding, the choice `SujetsWipView` had already made — a
redirect confirmed the id was real. Six tests pinned the old shape and were
rewritten to pin the refusal instead.

Regression coverage: `tests/c_e2e/modules/wip/test_wip_record_isolation.py`,
including the write half — the exploit's `POST` with the hidden `id`. Verified
to fail without the fix.

**Original recommendation, for the record.** Override `_get_model` on `AvisEnqueteWipView`. Every affected route enters through it — get, edit, ciblage, post, reponses, rdv, notify_publication — so one override closes them all. Two precedents already exist in the tree: `SujetWipView._get_model` (`sujets.py:290`), whose docstring calls this exact defect "security VULN-001" and spells out the reason, and `ArticlesWipView._require_author`. Prefer `NotFound` over `Forbidden`, as Sujet does, so the response does not confirm the record exists. The owner-scoped query already exists too: `OwnedRepository.get_owned` (`services/repositories/_owned.py`) — the view simply calls the wrong method.

### 2. An uploaded filename's extension decides the served MIME type — **high, new**

`src/app/lib/file_object_utils.py:68`, `src/app/modules/media/views.py:21,37`

`create_file_object` takes `ext = Path(original_filename).suffix.lower()` with no allowlist and stores `<sha256><ext>`. `/media/<name>` accepts `^[0-9a-f]{64}(?:\.[A-Za-z0-9]{1,10})?$` and serves with `mimetypes.guess_type(storage_name)`. `.svg` yields `image/svg+xml`; **`.html` yields `text/html`**, which I had missed and which is the sharper primitive.

I filed this at medium expecting a re-encode somewhere to kill it. There is none. `resized()` and `squared()` (`image_utils.py:100,119`) are the only Pillow re-encoders in `src/` and **have no callers** — I confirmed this independently. `ValidImageField` and `ValidImageFieldSquare` declare zero validators despite their names. `api/trix_blobs.py:20-30` performs no size or type check at all, and returns the media URL as **`href`** as well as `url`.

That `href` is the delivery vector: Trix inserts it as an attachment anchor, bleach preserves `a[href]` (`html_sanitize.py:87-89`), and a relative `/media/...` URL passes the protocol allowlist. One click inside a legitimately published article navigates top-level to same-origin active content.

The CSP that should have capped this is wide open: `etc/settings.toml:120-123` carries `script-src 'self' 'unsafe-inline' 'unsafe-eval'` with `img-src ["*", "data:"]` — inline script executes, and any host is a valid exfiltration target. Verified independently. `X-Content-Type-Options: nosniff` does not help: it prevents sniffing *away from* the declared type, and the declared type is the scriptable one.

**Fixed.** Two locks. `create_file_object` now stores only an allowlisted
extension (`safe_suffix`, `lib/file_object_utils.py`) — an allowlist, because
`.html` is as scriptable as `.svg` and a denylist would have to guess the whole
set; anything else is stored with no extension. And `/media` will only *name* a
type from `SERVABLE_TYPES`, falling back to `application/octet-stream`, which
covers the files stored before the first lock existed. `trix_blobs.py` gained
the size check every other upload path already had. A test pins that the two
lists agree: every extension kept maps to a type `/media` will serve, and none
of those is executable.

Not fixed here, and it deserves its own ticket: `script-src 'unsafe-inline'
'unsafe-eval'` in `etc/settings.toml`. Changing it needs testing this audit did
not do, and it is what turns any HTML-injection bug in this application into a
working one.

**Original recommendation.** An extension allowlist in `create_file_object` — an allowlist, not an SVG denylist, or `.html` walks straight through — plus `as_attachment=True` or a hard Content-Type allowlist in `media/views.py`. Add a size and type check to `trix_blobs.py`, which has neither. Separately, `'unsafe-inline'`/`'unsafe-eval'` on `script-src` deserves its own ticket: it is what turns any HTML-injection bug in this application into a working one.

## Confirmed in part

### 3. The deploy workflow runs a moving branch ref while its job holds the deploy token — **low, new**

`.github/workflows/fly-deploy.yml:14`

`uses: superfly/flyctl-actions/setup-flyctl@master` resolves a branch, not a commit. The token is in the *next* step's `env:`, not the action's — but same job, same runner, same filesystem, and the action's whole purpose is to put the `flyctl` binary on `PATH` that then receives `FLY_API_TOKEN`. Upstream `master` is branch-protected, which narrows the adversary to a merged malicious PR, a compromised maintainer, or Fly.io itself, without eliminating it. One extra unpinned link I had missed: the action's `version:` input defaults to `latest`, so pinning the action to a SHA still leaves the binary floating.

**Refuted within this finding:** `voxmedia/github-action-slack-notify-build@v1`. That repository is archived, so GitHub rejects tag writes and the ref cannot move. I had treated `@v1` as equivalent to `@master`; it is not.

**Coverage this establishes, which is worth as much as the finding:** there is **no expression injection** anywhere. All six `${{ }}` uses were enumerated; the only one inside a `run:` is `matrix.python-version` from a literal list in the same file. No `github.event.*`, `head_ref` or `actor` reaches any shell. Neither `pull_request_target` nor `workflow_run` is used.

**Fixed.** `fly-deploy.yml` is deleted. **Deleting the file does not revoke the
secret** — if `FLY_API_TOKEN` was ever created in the repository's settings, it
is still there and still valid, and that is a manual step in GitHub.

## Refuted

**F4 — the second app factory.** `src/app/__init__.py:23` does register the ontology admin blueprint at the URL root with no auth, and the Flask CLI would select it under `FLASK_APP=app`. But every route on that app 500s before touching data: the stub never calls `setup_config` or `db.init_app`, so `db.session` raises. It is unconditionally broken — no environment variable can make it work, only a code change. Nothing in the tree selects it. **Dead code to delete, not a latent trap.** I accept the refutation; my "one env var away" framing was wrong.

**F5 — `TESTING` authenticates anonymous requests as user 0.** Refuted as exploitable, because user id 0 cannot exist: autoincrement PK, the shipped dump `setval`s the sequence to 1, and `import_user` drops an explicit id. I accept it — but my *evidence* was wrong in a way worth recording, below.

## Arising during verification, not themselves verified

These came out of the refutation pass. None has been through a verification of its own, so none is a confirmed finding.

- **Communiqué and Commande share finding 1's shape.** `communiques.py:188` and `commandes.py:101` are role-only gates over the unscoped `_get_model`. Same fix.
- **`/BW` is the only module gate that reads `g.user`** (`bw_activation/__init__.py:42`) where `swork`, `wip`, `preferences`, `admin` and `biz` all use `current_user` — I verified this myself. It is the single line that would turn `TESTING` from a test convenience into an authentication bypass, and invariant 2 currently holds there by the accident of user 0 being absent rather than by the gate. `FLASK_TESTING` is settable from the environment (Dynaconf, `envvar_prefix="FLASK"`) with no start-up refusal — unlike `ACCEPT_ANY_PASSWORD`, which the team deliberately hardened to demand `UNSECURE` as well. The same variable also disables Talisman and the entire CSP (`extensions.py:134`), which is what caps finding 2.
- **`ci.yml` is dead.** It calls `nox -s check` and `nox -s test`; `noxfile.py` defines only `tests`, `lint` and `check_prod`. I verified this. Both jobs always fail and `build` never runs, so the CI signal that file appears to provide does not exist.
- **`lint.yml` and `tests.yml` run fork-PR code on `runs-on: ubicloud`** — third-party infrastructure registered as self-hosted runners. Secrets are withheld from fork PRs, so this is about the runner environment rather than credentials, but it is a larger surface than finding 3 and deserves its own look.

## Answered, 2026-09-09

1. **`FLY_API_TOKEN`** — Fly is not used. The workflow is deleted. One manual
   step remains that no code change can do: revoke the secret in the
   repository's settings if it was ever created.
2. **The repository is public**, and an outside pull request is not expected in
   practice. Both halves matter. Public means the CI surface has a real
   adversary rather than a theoretical one; "not expected" means the likelihood
   is low, not that the path is closed. The threat model has been corrected —
   it claimed a fork PR reaches repository write and the secrets, and it does
   not: GitHub withholds every secret from a fork's `pull_request` run and
   issues a read-only token whatever the repository settings say. The party who
   does reach them is a collaborator whose branch runs in-repo, or whoever
   controls an action a workflow calls.
3. **`permissions:`** — plainly: every workflow run gets an automatic
   `GITHUB_TOKEN`, and a `permissions:` block says what that token may do. With
   no block, it gets whatever the organisation's default is, which is invisible
   from this repository. Adding `permissions: contents: read` to a job that only
   reads code means that even if something malicious runs there, its token
   cannot write to the repository. It is a seatbelt, not a fix for a known
   defect: on this repository the default is very likely read-only already
   (GitHub changed the default for organisations created after February 2023,
   and this one dates from June 2024). The reason to add it anyway is that it
   makes the guarantee readable in the file instead of resting on a setting
   nobody checks. Cheap, one line per workflow — say the word and I will add it.

## Gaps in the threat model

- **The CI adversary line is overstated.** `threat-model.md:34` says anyone who can open a pull request gets "repository write, secrets, the publishing token". For a fork PR on a public repository, GitHub withholds all three. This inflates the severity of everything CI-related and should be narrowed to a collaborator whose branch runs in-repo.
- **The repository's visibility is not recorded**, and every CI conclusion depends on it.
- **`/media/<hash>` is missing from the entry-point table.** It is a session-independent read of every uploaded file where knowing the sha256 *is* the access control. That may be intended; the model should say so, because finding 2 lives there.
- **`fly-deploy.yml` holds a live credential for a path the user confirms is unused.** Either retire it or account for it.
- The **production deployment path is unknown**, so no invariant resting on an environment variable can be checked by reading this tree. That covers `ACCEPT_ANY_PASSWORD`, `UNSECURE`, `TESTING` and `FLASK_STRIPE_DEBUG_PASSWORD`.

Re-running `/bruce:model` after the first two points would be worthwhile.

## Coverage

**Audited.** The exposed surface: `flask/hooks.py`, `flask/doorman.py`, `flask/main.py`, `src/app/__init__.py`, the WIP CRUD views, `api_v1`, the Stripe webhook, `media/views.py`, `lib/file_object_utils.py`, `lib/image_utils.py`, the upload paths (banner, BW stage B1, article/communiqué/event images, KYC photo, trix blobs), `blueprints/ontology`, `modules/dashboard`, and the four workflow files.

**Stop conditions found, i.e. places the trace died safely.** The Stripe webhook verifies the signature before touching anything and returns on both failure branches (`stripe/views/webhook.py:181-198`). API v1 authenticates in `before_request` and enforces capability scopes per resource (`api_v1/resources.py:65`). The `/media` path regex forbids arbitrary storage paths. The `queue` blueprint's routes are commented out — dead, not exposed. The doorman covers `/admin/`, and `ontology_bp` is mounted under it in the real factory. `biz` H1's fix holds.

**Not covered.** Everything outside the exposed surface: the service layer's business logic, `modules/swork`, `modules/wire`, `modules/biz` internals, the Dramatiq actors, the CLI, the faker, and the 2.8 MB of `src/` the byte ceiling would have dropped had the scope not been narrowed on purpose. No test file was audited. No dependency review, no secret scanning of git history, and nothing about the running deployment — configuration, TLS, database permissions, S3 bucket policy — which is where three unresolved questions in this report actually live.
